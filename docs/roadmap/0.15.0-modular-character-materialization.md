# Blender Research MCP 0.15.0 — modular character materialization

- Status: implementation in progress
- Target package and bundled add-on version: `0.15.0`
- Protocol: `1`
- Transaction capability: `10`

## Purpose

0.15 closes the smallest generic pipeline needed to turn a constrained character
source into editable modules without applying destructive operations to that source:

```text
mesh.materialize -> mesh.extract -> rig.bind
```

The tools operate on ordinary Blender evidence and do not encode hair, clothing, body,
or project-specific names.

## Public surface

- `mesh.materialize` creates an independent Mesh object from explicit `BASE`,
  `SHAPE_KEYS_CURRENT`, or `FINAL_EVALUATED` evidence and verifies requested material,
  UV, and weight domains.
- `mesh.extract.preflight` proves a FACE SelectionSet is a bounded proper subset and
  reports connected-component and output-size evidence without writing.
- `mesh.extract` removes one or more selected face islands from the source branch and
  creates one new object with exact SOURCE and EXTRACTED ComponentMaps.
- `rig.inspect` pages exact Armature, bone, Modifier, group-match, and unweighted-vertex
  evidence for one Mesh object.
- `rig.bind` creates or updates one exact Armature Modifier and applies explicit
  object-parent semantics without modifying weights.

## Evaluation boundary

`BASE` is stored topology. `SHAPE_KEYS_CURRENT` is current Shape-Key deformation with
all Modifiers excluded. `FINAL_EVALUATED` is the complete current dependency graph and
must be backed by a live SurfaceRef. The final mode reports baked Armature deformation
and is not automatically treated as a reusable rest mesh.

Materialization is creation, not Apply. The source object, Shape Keys, parent, and
Modifier stack stay unchanged. Output mappings are exact only when source and result
topology match.

## Extraction and assembly boundary

Extraction accepts disconnected FACE regions but still requires a non-empty proper
subset and returns one new object. Parent, Modifier, and material-slot policies are
explicit. Binding validates existing groups against bones; UV/weight transfer and
normalization remain separate 0.14 operations.

## Compatibility and limits

The protocol, 1 MiB request, 32 MiB response, 30 second command deadline, geometry
budgets, Blender 4.2.23, and Python 3.11 targets remain unchanged. A 0.15 server can use
all older tools against a 0.14 add-on; only the new tools require their new capabilities.

0.15 does not add ComponentCatalog, Collection creation, generic parenting, cross-object
batches, library append, templates, Shape-Key structure writes, Modifier Apply,
arbitrary BMesh/RNA/Python, or retopology.

## Acceptance

Automated tests cover all three evaluation modes, evidence drift, output copy domains,
multi-component extraction, exact rig creation/update/no-op, transaction recovery,
native-save adoption, compatibility, schemas, package resources, and response budgets.

The Blender 4.2.23 gate uses deterministic Shape-Key/Armature/attribute fixtures and a
temporary copy of `test-model.blend`. It proves source immutability, module extraction,
idempotent binding, whole-chain rollback/disconnect recovery, commit/save/reload, UI
preservation, and unchanged source-file hashes.

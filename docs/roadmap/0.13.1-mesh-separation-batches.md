# Blender Research MCP 0.13.1 — Mesh separation and declarative batches

- Status: implemented and validated on Blender 4.2.23 LTS
- Target package and bundled add-on version: `0.13.1`
- Protocol: `1`
- Transaction capability: `8`
- Mesh topology capability: `3`
- ComponentMap capability: `2`

## Purpose

0.13.1 turns one-revision topology evidence into a bounded workflow surface. It adds
public map composition, exact object-local separation of one connected face region,
and an atomic Mesh-only batch that names intermediate resources and automatically
remaps them after topology changes.

## ComponentMap composition

`mesh.component_map.compose` accepts two to eight maps whose object, Mesh identity,
revision, and fingerprint endpoints match exactly. It follows only recorded same-domain
lineage and returns an ordinary bounded ComponentMap resource with source map IDs, step
count, map kind, and ordered transaction IDs. The result supports existing inspection,
release, and SelectionSet remapping. The final endpoint must still be live.

## Connected face-region separation

`mesh.separate` accepts one revision-bound FACE SelectionSet that is non-empty,
connected, and smaller than the complete source Mesh. It leaves true Blender selection
untouched. A shared Mesh is single-usered only for the target object; peer objects keep
their original data.

The new object inherits the independent-duplicate object shell and owns a new Mesh.
The response contains source and separated branch maps, rebound selections on both
branches, exact object/Mesh evidence, and protected-attribute effects. Rollback restores
the source data relationship and removes the new object; commit keeps both branches.

## Declarative Mesh batches

`mesh.batch.execute` accepts one to eight exact initial Mesh targets, one to thirty-two
closed steps, at most eight topology or separation steps, and at most sixty-four
aliases. Steps are limited to existing SelectionSet query/derive, selection-driven Mesh
edit, Mesh separation, and bounded Mesh validation assertions.

Static preflight occurs before mutation. During execution every target branch tracks
its current evidence and map chain; all affected SelectionSet aliases are remapped
after topology changes. A runtime failure rolls back the complete active transaction.
A successful batch advances global generation once, while every step retains its own
Mesh revision, fingerprint, map, and validation report.

## Compatibility and limits

New capabilities are `mesh_separation: 1`, `mesh_batch: 1`,
`mesh_component_map: 2`, `mesh_topology: 3`, and `transactions: 8`. A 0.13.1 server can
continue using older tools with a 0.13 add-on; only composition, separation, and batch
execution require the new capability vector.

The existing 1 MiB request, 32 MiB response, 30-second deadline, transaction delta,
resource-book, and geometry budgets remain. Batch aliases are invocation-local even
though returned SelectionSets, SurfaceRefs, and ComponentMaps remain session resources.
No arbitrary BMesh operation, RNA path, Python, UV/weight write, Shape-Key write,
Modifier Apply, or evaluated-mesh materialization is added.

## Acceptance

Automated gates cover map composition semantics and budgets, both separation branches,
protected data, transaction lifecycle, batch preflight and runtime rollback, alias
remapping, generation suppression, idempotency, compatibility, packaging, and skills.

The Blender 4.2.23 gate uses deterministic topology fixtures plus a temporary copy of
`test-model.blend`. It composes chains across transactions, separates a connected region
from shared data, continues on both branches through aliases, surface-fits and validates
an independent proxy, proves rollback/disconnect/native-save behavior, and leaves the
source file unchanged.

UV and weights remain 0.14. Shape-Key writes, evaluated Mesh materialization, and
Modifier Apply remain 0.15.

# Blender Research MCP 0.7.0 — managed application and project lifecycle

- Status: implemented and live-validated on Blender 4.2.23
- Target package and bundled add-on version: `0.7.0`
- Protocol: `1`
- Blender target: `4.2.23 LTS` / Python `3.11`

## Outcome

0.7.0 lets an Agent operate Blender without requiring the user to start the
application or preinstall the add-on. Application launch and project opening are
deliberately separate semantic tools so the Agent can follow the user's actual intent:

~~~text
open Blender only
  application.status -> application.launch if needed

open a project
  application.status -> application.launch if needed -> project.open
~~~

An explicit request to save, switch, reload, or close is sufficient authority for the
corresponding operation. The lifecycle tools do not add a second confirmation or a
project-root allowlist.

## Managed application contract

`application.status()` returns `running=false` normally when no compatible MCP session
exists. A running result includes PID, instance ID, Blender/add-on versions, port,
managed status, launch ID, capability versions, and current project summary. It never
returns the session token.

`application.launch()` accepts no project path. It reuses one compatible advertised
session or starts the configured Blender with exact argument-array execution:

1. CLI `--blender-executable`;
2. `BLENDER_RESEARCH_MCP_BLENDER_EXECUTABLE`;
3. `blender` from `PATH`.

Calls are serialized by one asynchronous lock. A new launch receives a UUID launch ID,
port and fixed add-on resource environment, and a local log. Success requires a new
manifest with that launch ID, authenticated handshake, and
`application_lifecycle >= 1`. The launch timeout is configured by CLI
`--launch-timeout` or `BLENDER_RESEARCH_MCP_LAUNCH_TIMEOUT_SECONDS`, defaulting to 90
seconds. The server never closes Blender merely because the STDIO MCP process exits.

`application.quit(save_current=true, save_current_as=null)` commits the active
transaction and saves a dirty current project by default, then schedules quit for the
next Blender main-thread tick. A dirty untitled project needs `save_current_as`.
`save_current=false` directly discards unsaved state. External success requires both
the process and its instance manifest to disappear.

## Session-level add-on bootstrap

The wheel contains the single repository add-on source through Hatch `force-include`
and a fixed bootstrap resource. Development editable installs locate the same source
tree through an explicit fallback; built wheels use the packaged resource path.

Before launch, the resource bytes are hashed and atomically materialized under:

~~~text
%LOCALAPPDATA%\blender-research-mcp\managed\0.7.0\<sha256>\
~~~

The bootstrap adds only that fixed add-on directory to the session path and calls the
Blender add-on API with session persistence. It does not write preferences, save a
startup file, accept user Python, or forward arbitrary Blender command-line arguments.
The implementation follows Blender's documented ordered `--python` execution and
persistent main-thread timer contracts:

- <https://docs.blender.org/manual/en/4.2/advanced/command_line/arguments.html>
- <https://docs.blender.org/api/4.2/bpy.app.timers.html>
- <https://hatch.pypa.io/1.10/config/build/>

## Project contract

All project paths are absolute and end in `.blend`. Open targets must exist. Save and
Save As targets may be new when their parent directory exists. Existing Save As targets
are overwritten without a file selector.

`project.status()` does not depend on `VIEW_3D`; it returns filepath, saved/dirty state,
scene generation, active transaction summary, and the most recent lifecycle operation.

`project.save(path=null)` first validates and commits any active transaction. Without a
path it saves the current named project; an untitled project requires a path. A
different path performs Save As and makes the result current.

`project.open(path, save_current=true, save_current_as=null, use_scripts=true,
load_ui=true)`:

1. validates the target before changing the current project;
2. commits an active transaction when `save_current=true`;
3. saves a dirty named current project or uses `save_current_as` for a dirty untitled
   project;
4. returns `accepted`, then opens on the next main-thread tick;
5. reconnects and verifies the exact resulting absolute path;
6. returns before/after project, transaction, save, and operation evidence.

Opening the current path returns `already_open` after any required save. With
`save_current=false`, the old file is switched directly and `load_post` abandons the
old transaction and clears file-local evidence and idempotency state.

`project.reload(save_current=false, use_scripts=true, load_ui=true)` reloads the current
saved path. Its default deliberately discards unsaved changes; `save_current=true`
commits and saves first. An untitled current project returns
`PROJECT_RELOAD_UNAVAILABLE`.

The Blender implementation uses documented WM operators and checks their result:
<https://docs.blender.org/api/4.2/bpy.ops.wm.html>.

## Capability and compatibility

The add-on advertises:

~~~json
{
  "project_lifecycle": 1,
  "application_lifecycle": 1
}
~~~

The external 0.7 server keeps the 0.6 observation/comparison capability vector as its
global connection requirement. A 0.6 add-on can therefore continue serving old tools;
only a lifecycle tool raises `CAPABILITY_MISMATCH` when its local capability is absent.

Lifecycle mutations generate one UUID idempotency key per logical bottom-level command
and reuse it across transport retry. A separate complete MCP invocation runs its
requested operation again.

## Stable failures

- `APPLICATION_NOT_RUNNING`
- `BLENDER_EXECUTABLE_NOT_CONFIGURED`
- `BLENDER_EXECUTABLE_NOT_FOUND`
- `APPLICATION_LAUNCH_FAILED`
- `APPLICATION_LAUNCH_TIMEOUT`
- `APPLICATION_QUIT_TIMEOUT`
- `PROJECT_PATH_INVALID`
- `PROJECT_NOT_FOUND`
- `CURRENT_PROJECT_UNTITLED`
- `PROJECT_SAVE_FAILED`
- `PROJECT_OPEN_FAILED`
- `PROJECT_OPEN_TIMEOUT`
- `PROJECT_PATH_MISMATCH`
- `PROJECT_RELOAD_UNAVAILABLE`

The add-on also records an operator-level failure in `project.status.last_operation`
when a previously accepted next-tick open, reload, or quit does not finish.

## Automated acceptance

The automated suite covers executable and timeout precedence, exact argv/environment,
no-shell process creation, launch coalescing, manifest launch IDs, early exit, resource
materialization, old add-on compatibility, tool annotations/schema, absolute paths,
Save/Save As, trusted script/UI forwarding, next-tick scheduling, reconnect/path
verification, operation failure, reload defaults, and quit completion. Add-on sources
continue to parse as Python 3.11.

Each implementation checkpoint runs:

~~~powershell
uv run --no-sync pytest
uv run --no-sync ruff check .
uv run --no-sync mypy
~~~

## Real Blender acceptance

The completed live gate started with no MCP Blender session and only a configured
Blender executable. It recorded:

- cold `application.status -> application.launch`, PID, launch ID, versions,
  capabilities, heartbeat, and repeated-launch reuse;
- temporary `.blend` copies and unchanged source SHA-256 values;
- active transaction commit plus default current-project save before `project.open`;
- Save, Save As, same-project no-op, reload discard, and reload-save behavior;
- default trusted script loading plus one `use_scripts=false` case;
- default saved quit, manifest removal, and a second cold launch;
- current path and lifecycle state visible in the full Scene Properties panel.

The evidence is recorded in
[`docs/validation/2026-08-29-managed-lifecycle.md`](../validation/2026-08-29-managed-lifecycle.md).
The independent 0.6 comparative preview smoke remains pending.

# 多任务、多工作树并行开发与串行集成计划

- 日期：2026-09-05；状态：开发组织计划，尚未创建工作树或启动实现任务。
- 功能范围与验收以[新 issue 路线](2026-09-05-rendering-and-animation-review.md)为准。
- 用户允许后续由主任务组织多个独立 Codex 任务，在不同 Git 工作树中开发。
  本轮先冻结分工；启动实施时按本计划创建任务，不把文档更新当作任务已经运行。

## 1. 组织方式与并行上限

采用 **1 个集成任务 + 最多 3 个开发任务** 的初始配置。集成任务负责契约、公共入口、
验收与发布状态；开发任务拥有独立工作树、分支、uv 环境、提交和测试产物目录。
这是保守调度起点，按设备和实际任务容量调整，不代表工具固有并发上限。

不按“一个 issue 一个完全独立版本”拆分。代码中 `server.py`、`state.py`、protocol、
上下文及事务恢复是共同修改点，四个 issue 同时修改它们会增加语义冲突。
先限定核心接口，开发功能模块，再由集成任务接入共享入口。
工作包在不同工作树中并行，**集成和版本发布串行**；不能把分支测试通过当作组合后通过。

每个新任务的第一条指令必须包含：

1. 目标与不包含的功能，基线 commit SHA、自己分支和工作树绝对路径。
2. 独占可写文件、新模块目录、禁止修改的公共文件，以及所用契约版本。
3. 要复现的输入、成功/失败/恢复验收和历史证据的局限。
4. 测试命令、独立端口/临时根、Blender 资源预约方式及原始资产只读规则。
5. 提交与交接格式；不得自行升级产品版本、合并到集成分支、发布或关闭 issue。

分支名为实施时建议值，均使用 `codex/` 前缀。每个实际任务使用创建工具返回的真实
task/thread ID、host ID 和工作树路径；不预造 ID，也不把同一个目录登记成多个开发身份。

| G：`mesh-quality-consistency` | QLT-01/02；add-on `mesh_patch_quality.py`、`mesh_local_quality.py`、`mesh_surface_ops.py`、`mesh_topology_ops.py`；专用几何夹具与测试 | 这两项共享局部检查内核，合为一包；交付实际三角化、写后门和 scoped target 检查 |

`blender_addon/blender_research_mcp_addon/`。测试优先新建工作包专用文件，避免所有任务
同时修改 `tests/test_server.py`、`tests/test_addon_package.py` 或同一实机总入口。

**I 独占的公共修改点：**

- `src/blender_research_mcp/server.py`、`protocol.py`、`constants.py`、`context_policy.py`；
- add-on `state.py`、`runtime.py`、`transaction_model.py`、`structural_ops.py`、

- README、design、需求主文档、路线图和阶段验收总记录。

开发任务可以提出这些文件的具体接线清单或补丁建议，但不直接提交跨所有权修改。
若功能离开公共入口无法测试，先以封闭 handler/模块测试；I 在集成工作树接线后跑公开
MCP 路径验收。完整阶段完成仍要求公开入口实机门，不以直接 handler 测试代替。
确需改变所有权时，由 I 记录文件、任务、基线和有效窗口后再改，不能“先改了再解决冲突”。

## 3. 先冻结的最小共同契约

实施启动后先由 I 做一个小型契约提交 C0：

- QLT scoped 源面集合、问题证据与恢复字段；位移误差输出与硬上限含义。
- `VIEWPORT/CAMERA_RENDER` 证据选择及版本化渲染配置清单。
- frame/subframe、View Layer、非目标依赖与用户原生保存接管规则。
- 模板声明/依赖闭包与克隆报告的输入输出边界；新增 delta 的恢复责任。
- capability 协商、未知键兼容及本阶段保留的旧请求行为。

C0 先写足以避免冲突的 schema/类型和约定，不提前实现完整任务框架，也不广告未交付能力。
所有任务记录 C0 SHA；G/D 可在契约确认后立即开发，L/M 以各自已确定的接口推进。
J 的状态机、冻结输入与取消语义在 J 原型结束时形成 C1；T 采样依赖 C1，TMP-01 不依赖它。
开发任务发现契约不足时提交具体问题与例子，I 修改契约并通知依赖任务。
不在各工作树各自发明同名但含义不同的字段。

## 4. 波次、启动条件与合入次序

| 波次 | 同时工作的开发任务 | 集成任务的独立工作 | 退出条件 |
| --- | --- | --- | --- |
| W0 | 尚未启动功能开发任务 | 核对 Git/未跟踪文件，建立 I 工作树，冻结 C0、文件归属及测试端口表 | 可复用基线 SHA 与任务说明完整 |
| W1 | G、D、L | 接入 scoped/数值字段；审核 QLT 复现，准备合成场景与兼容测试 | G/D 各自提交并通过分支门；L 可继续进行 |
| W2 | L、M、J 原型 | 串行合入 G、D，完成 0.17.6 合并后门；让剩余任务显式更新到该 SHA | L 的相机证据可用于 M 验收；J 给出设备/取消原型结论 |
| W3 | M 收尾、J 正式实现、T 的只读依赖检查 | L → M 串行合入并完成 0.17.7；冻结 C1 | J 正式实现必须基于 L 已合入版本；TMP-01 可单独交接 |
| W4 | T 的有限帧采样 | J 合入与 0.17.8 长任务压力门，再整合 T 完成 0.17.9 | 每个阶段自己的公开路径、恢复和产物验收通过 |

L 尚未合入时，J 只做拥有独立文件的原型，不抢改 `world_render_ops.py`。
有空余任务槽时优先推进已具备契约的工作，不为了占满并发而创建尚无可执行输入的任务。
如果 G/D 延迟，L/M 的独立模块工作可以继续；0.17.6 的正确性门仍先于新阶段发布。

每次新任务从最近已验证的 I 分支明确 SHA 建立工作树。已有任务升级基线时先提交自身进度，
再在自己的分支合入 I 的明确提交；不让 I 切换运行中开发任务的分支或代为硬重置。
若选用 rebase，必须确认该分支无人共用；默认使用显式集成提交以保存交接历史。

## 5. 工作树与任务创建流程

1. I 先核对保存项目是否为 Git 仓库、当前分支、工作树清单和 dirty 状态，保存已有未跟踪
   文件清单。主目录不承担并行开发，不复制用户 IDE 配置和缺陷报告到其他分支。
2. 为 I 建立独立 `codex/` 集成分支/工作树；随后通过项目任务创建能力启动开发任务，
   Git 项目选择 worktree，明确从已存在的 I 分支/基线开始。创建前读取项目清单并验证仓库身份。
3. 创建是异步的：等实际任务和工作树 ready 后才发执行信息，记录真实 task ID / host ID；
   setup 中的 clientThreadId 不能当作已运行 task ID 调用其他工具。
4. 每棵工作树按项目工具链 `uv sync` 建立自己的环境，继续使用宿主共享 uv cache；
   常规命令 `uv run --no-sync`。不共享 `.venv`，不迁移 cache，不靠直接 Python/pip 绕过环境。
5. 各任务核对自己的 AGENTS/design、分支和 SHA。需要 APO 时按该工作树的绝对路径
   独立登记并取得快照；不能把主工作树的 snapshot 当作当前树证据。普通阅读不自动刷新。
6. I 通过任务消息与有 cursor 的状态等待协调，优先读取最终交接与可行动变化。
   对用户说明实际任务名称、目标和状态；不高频重复拉取没有变化的完整历史。

任务创建、工作树和本地实现可在用户开启实施阶段时按计划执行；push/PR merge、公开 issue
评论/关闭和删除分支/工作树另按当时的用户授权处理。尤其不能因某任务结束就自动清理其证据。

## 6. Blender、端口和真实资产的并发边界

- Python 静态/单元测试可并行；每任务用工作树内独立 artifacts 子目录、临时路径和唯一运行 ID。
- 本机原生 Blender 验收默认只放行一个重型实例；GPU 相机/生产渲染串行预约。
  是否放开轻量 headless 几何测试并发由实测 CPU/内存决定，不能把两个同时超载的失败当作产品缺陷。
- 每个测试实例分配独立 loopback 端口、session token、Blender user config、启动文件和日志路径，
  启动前确认端口未占用；禁止各分支使用同一个开发端口 9877 或修改共享 add-on 安装。
- 实例从对应工作树打包/加载，并报告 Git SHA、add-on 版本、Blender build 和连接身份。
  不能连接别的任务的 Blender 后声称验证了自己的分支。
- 真实 `.blend` 输入开始/结束核对 SHA，各任务只操作 `blender-projects` 下自己的独立验收副本；
  同一个角色副本、PNG 目标、审计 JSON 和 checkpoint 不允许并行写。临时 worker 的所有权
  核对、取消和清理只作用于自己的实例。
- 真实角色整合验收由 I 在已集成版本执行，艺术评价单列。开发任务的合成夹具可以随仓库分发，
  角色资产、纹理、图像和项目专用自动化留在渲染项目。

## 7. 交接、集成和失败处理

每个任务在关键节点提交，只提交自己拥有的实现/测试/专用记录。交接至少包含：

```text
工作包 / 实际任务 ID / 工作树绝对路径 / 分支
基线 SHA / 契约版本 / 可集成的 commit SHA 列表
修改文件 / 需要 I 完成的公共入口与恢复接线
新增行为 / 保留旧行为 / 已知限制与未完成范围
pytest / Ruff / mypy / Python 3.11 / 原生与 socket 证据路径
真实或合成输入、版本、恢复和 UI 响应证据；未跑的门明确写未跑
```

I 每次只集成一个包：核对所有权与干净提交 → 审查差异 → 合入明确 SHA → 完成入口接线 →
运行对应组合门 → 记录新 I SHA → 通知依赖任务。采用显式 merge 或逐个 cherry-pick，
不要从开发任务的未提交工作区复制文件，也不要在用户主目录做整包覆盖。

开发分支执行项目提交门；I 在每个正式阶段执行完整 `pytest`、`ruff check .`、`mypy`、
Python 3.11/包版本检查及本阶段实机门。组合后重点覆盖：

- G 的写后拒绝与 D 的误差失败在单次/batch 中都恢复正确；
- M 的实例、图像及嵌套组恢复能被 L 的 compare 生命周期完整验证；
- J 的冻结输入、取消和结果文件与 L 的渲染清单一致；
- T 的帧/子帧资源不会绕过 G 的选区范围、J 的输入与取消约束；
- 新旧 capability、原生保存、用户修改、断连及 UUID 重放保持明确语义。

若分支门通过但集成门失败，I 保留失败证据，将可定位修复交回原任务或做专注集成修复；
该阶段不标为完成。不通过放宽输入护栏、删除验收、刷新 guard 接受用户数据漂移来消除冲突。
只有已验证的 I SHA 才是下一波工作树的起点，某个任务先完成不决定谁先发布。

这个分工把能独立实现的几何、数值、相机和模板工作并行，同时把协议、事务恢复、
Blender 资源和阶段验收留给明确的单一负责人。

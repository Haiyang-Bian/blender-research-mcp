# Blender Research MCP 0.6.0 — reversible comparative previews

- Status: implemented with automated coverage; real Blender acceptance passed on
  2026-08-30
- Target package and bundled add-on version: `0.6.0`
- Compatible Blender target: `4.2.23 LTS`
- Local protocol: `1`
- Required existing add-on capabilities: viewport capture `3`, transactions `2`,
  LookDev inspection `1`, and the relevant writer capability `1`

## Goal

Turn the current manual sequence—baseline capture, one preview, evidence, rollback,
repeat—into one bounded MCP operation:

~~~text
inspect exact target
  -> capture baseline
  -> preview candidate A -> capture -> rollback -> verify baseline
  -> preview candidate B -> capture -> rollback -> verify baseline
  -> optionally preview candidate C -> capture -> rollback -> verify baseline
  -> return ordered evidence without selecting a winner
~~~

The milestone improves speed and consistency without adding new Blender mutation
authority. It composes the already validated 0.5.1 writers and does not introduce a
generic RNA path, arbitrary Python, file saving, or automatic artistic approval.

Real Blender 4.2.23 evidence, including ordered candidates, same-property conflict
preservation, disconnect rollback, context restoration, and unchanged fixture hashes,
is recorded in `docs/validation/2026-08-30-comparative-previews.md`.

## Public interface

Add one MCP tool:

~~~text
lookdev.compare(
    target,
    candidates,
    capture
)
~~~

The tool is closed-world, idempotent for the same full payload, non-destructive in its
intended final state, and still marked as a mutation because Blender properties are
temporarily changed during execution.

### `target`

`target` is a discriminated union. Every form identifies exactly one writable property
and includes the session identities returned by the existing inspection tools:

- `object_scale_axis`: one object and exactly one local axis, `x`, `y`, or `z`;
- `object_visibility`: one of `hide_viewport` or `hide_render`;
- `modifier_state`: one modifier and one of `show_viewport` or `show_render`;
- `shape_key_value`: one non-Basis, undriven shape key;
- `material_input`: one exact material slot, material, node, and unlinked/undriven
  writable socket, including material user scope and shared-material confirmation.

The comparison tool must re-inspect the target before the baseline and before every
candidate. Names alone are never sufficient authority. It may strengthen the scale
path by requiring the object identity even though the lower-level 0.5.1 scale writer
accepts only the exact object name.

### `candidates`

- One to three entries, preserving request order.
- Each entry has a short unique label and one absolute value of the target's exact
  type.
- Candidate values must be unique and different from the observed baseline.
- Numeric values must be finite and remain inside the inspected range.
- Boolean properties naturally permit only one candidate opposite the baseline.
- No incremental expressions, relative offsets, clamps, or implicit type conversion.

### `capture`

The capture specification reuses `viewport.capture` semantics:

- exact evidence object name;
- one semantic view, optionally with the existing bounded absolute orbit;
- `CURRENT`, `WIREFRAME`, `SOLID`, `MATERIAL`, or `RENDERED` display mode;
- overlay policy;
- maximum size from 256 to 1000 pixels.

The response contains at most four images: the baseline followed by one image per
candidate. This keeps the worst-case response inside the existing 32 MiB bound.

## Execution contract

1. Settle scene generation and record full context, evidence object, and target state.
2. Capture the baseline and retain its generation, hash, matrices, and image bytes.
3. For each candidate, in request order:
   - re-inspect identities, property value, material scope, context, and generation;
   - begin a new transaction with a unique internal idempotency key;
   - call exactly one existing writer with the candidate's absolute value;
   - settle the scene and capture evidence;
   - roll back using the returned generation;
   - verify the property, context, and evidence object match the original baseline.
4. After the final candidate, perform one more settled baseline verification.
5. Return evidence only when every candidate completed and the final state is restored.

The operation must yield between bridge calls so Blender's main-thread timer and UI
heartbeat continue to run. It must never keep a transaction open while waiting for
human feedback.

## Result

Return MCP image content in this order:

1. baseline;
2. candidate A;
3. candidate B when present;
4. candidate C when present.

Structured output includes:

- exact inspected target and baseline value;
- baseline context, object, scene generation, capture metadata, and content index;
- each candidate label, requested value, writer before/after result, capture metadata,
  rollback result, content index, elapsed time, and scene generations;
- SHA-256 for every image;
- maximum channel difference, mean absolute difference, RMS difference, and structural
  mean absolute difference relative to the baseline;
- `context_unchanged`, `target_restored`, `object_unchanged`, heartbeat start/end, and
  total elapsed time;
- warnings for visually indistinguishable candidates without treating them as errors.

The tool does not return a `best_candidate`. Selecting a result is a human or caller
decision. Applying the selected value later requires a new explicit standard
transaction; comparison itself never commits.

## Failure and recovery

- Any scene, context, identity, material-user, or property drift stops all remaining
  candidates.
- A safe rollback is attempted only while the current value still equals the tool's
  last write. No force path exists.
- A conflict preserves user state and returns the original stable error code plus the
  failed candidate label and phase.
- Invalid or black capture evidence stops the comparison and is never returned as a
  completed candidate set.
- If rollback or final verification cannot prove baseline restoration, return a stable
  `COMPARISON_RESTORE_FAILED` error and leave the add-on's existing conflict state
  visible in the UI.
- Disconnect uses the existing transaction rollback path. Reconnection must verify the
  property and context before any new comparison begins.

## Implementation checkpoints

### 1. Typed comparison and image-difference model

Commit: `feat(comparison): add typed candidate and evidence models`

- Add discriminated target schemas and target-specific candidate validation.
- Extract deterministic image-difference statistics from the live-smoke helpers into a
  tested production module.
- Bound labels, candidate count, image dimensions, and structured output.
- Cover invalid unions, duplicate/baseline values, non-finite values, and socket/vector
  type mismatches.

### 2. Reversible orchestration

Commit: `feat(comparison): orchestrate rollback-safe candidate previews`

- Implement one transaction per candidate in the external service.
- Reuse existing inspectors, writers, capture settling, and error contracts.
- Verify baseline property and context after every rollback.
- Add structured phase/candidate details without masking existing bridge errors.
- Mark the MCP tool with mutation, idempotent, and closed-world annotations.

### 3. Operator workflow, UI, and Skill

Commit: `docs(skill): add comparative LookDev review workflow`

- Update README, usage guide, design handoff, and the unified
  `blender-research-workflow` Skill.
- Show active comparison phase and candidate label in the full Scene Properties panel;
  keep the N-panel compact.
- Make clear that comparison never commits and that a chosen candidate must be applied
  separately.
- Build the 0.6.0 add-on ZIP. The 0.6 server may accept a running 0.5.1 add-on when its
  negotiated capability vector is sufficient; compatibility is capability-based, not
  guessed from a version string.

### 4. Real Blender acceptance

Commit: `test(blender): record 0.6.0 comparative preview smoke`

- Use a fresh `%TEMP%` copy and preserve source hash and source Git state.
- Discover, rather than guess, one scalar shape-key or material target.
- Compare baseline plus two or three finite absolute candidates while the operator can
  watch the candidate label, active command, and rollback state in Blender.
- Verify ordered non-black images, difference statistics, heartbeat progress, and full
  restoration after every candidate.
- Inject one same-property manual edit during a candidate; require conflict preservation
  and stop remaining candidates.
- Disconnect during one candidate and verify automatic rollback before reconnecting.
- Confirm no comparison path exposes commit, saves the blend file, or changes the
  user's selection, mode, active object, viewport, or material scope.
- Keep one brief obscured-window capture as a secondary regression rather than the
  primary acceptance narrative.

## Automated gate

Every implementation checkpoint must pass:

~~~powershell
uv run --no-sync pytest
uv run --no-sync ruff check .
uv run --no-sync mypy
~~~

Required new coverage includes schema and annotation snapshots, all target variants,
candidate ordering, idempotent replay, response bounds, image statistics, per-candidate
rollback, context/identity/property conflict, disconnect rollback, and final baseline
verification. Add-on source must continue to parse as Python 3.11.

## Explicit exclusions

0.6.0 does not add:

- light, world, camera, exposure, or color-management writes;
- arbitrary modifier parameters;
- object location or rotation;
- node creation, deletion, rewiring, or material copying;
- asset import, project-script execution, arbitrary Python, telemetry, or file saving;
- automatic candidate ranking, approval, commit, promotion, or persistence.

After 0.6.0 is live-validated in a real LookDev decision, the next authority proposal
should choose exactly one domain—bounded existing-light energy/color or one reviewed
modifier family—and repeat the same inspect, preview, evidence, rollback process.

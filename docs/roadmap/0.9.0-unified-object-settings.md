# Blender Research MCP 0.9.0 — unified typed object settings

- Status: implemented; automated gate passed; Blender 4.2.23 acceptance pending
- Target package and bundled add-on version: `0.9.0`
- Protocol: `1`
- Structural transaction capability: `3`
- Object settings capability: `1`

## Purpose

0.9.0 gives Agent workflows one object-level setting operation without exposing generic
RNA or multiplying public Light and Camera tools. `object.set` applies one to four
distinct typed patches for an exact object. It is intended for coherent changes such as
moving a Camera while changing its lens, or changing an Area light transform, energy,
color, shape, and size.

Creation, duplication, deletion, active-Camera selection, materials, World, Modifiers,
images, and rendering remain separate semantic operations. The public entry is unified;
the Blender implementation still uses typed transform, visibility, Light, and Camera
handlers.

## Contract

`object.inspect` now reports visibility plus typed Light/Camera data identity, user
count, shared/library state, current values, writable fields, and ranges.

`object.set` accepts one to four non-repeated patches:

- absolute local location, XYZ Euler degrees, and scale;
- viewport/render visibility;
- common and type-specific Point, Spot, Sun, and Area settings;
- perspective or orthographic Camera optics, clipping, scale, and shifts without
  changing projection type.

The entire request is validated and transaction capacity is reserved before mutation.
Application order is transform, visibility, then object data. A successful multi-patch
request records up to three delta families and advances generation once. A no-op records
nothing and leaves generation unchanged. If a later field fails, earlier writes from
that same request are restored and verified; an unprovable restoration returns
`OBJECT_SETTINGS_RESTORE_FAILED`.

Shared Light or Camera data requires exact inspected identity and users plus
`allow_shared_data=true`. Linked data remains read-only. Existing
`object.transform`/`object.visibility.set` schemas use this same kernel; in particular,
a no-op transform no longer creates an empty transaction delta.

## Comparison

`lookdev.compare` adds the closed `object_setting` target. Its locator identifies one
transform axis, visibility flag, Light property, or Camera property. Numeric, Boolean,
Area-shape, and hexadecimal sRGB candidates retain their original JSON representation
in the report. Colors are converted to linear RGB for write/restore comparison, while
hex case variants are treated as the same candidate.

Every candidate still receives its own begin, one `object.set`, capture, rollback, and
restoration verification cycle. The tool does not pick a winner, commit, or save.

## Compatibility and boundaries

The protocol remains version 1 and transactions remain capability 3. A 0.9 server can
use the pre-existing 0.8 tool surface against a 0.8 add-on. Only `object.set` and an
`object_setting` comparison require `object_settings: 1` and otherwise return
`CAPABILITY_MISMATCH`.

The release does not add separate `light.set`/`camera.set`, arbitrary RNA, Camera DOF,
projection changes, Modifier parameters, arbitrary nodes, mesh-component editing,
animation, compositor control, or arbitrary Python.

## Acceptance

The automated suite covers closed schemas, strict values and ranges, typed data guards,
shared-data authorization, atomic multi-patch application, no-op behavior, capacity
preflight, apply/restore failures, transaction values, comparison routing and recovery,
annotations, capabilities, packaging, and Python 3.11 syntax.

The real Blender gate uses an isolated port and temporary `.blend` copies. It checks all
four Light types, perspective and orthographic Cameras, shared-data rejection/approval,
combined Camera transform/lens commit and rollback, typed comparisons, persistence
through save/reload, reviewed rendering, heartbeat progress, and source SHA-256
preservation. Its evidence is recorded separately after the gate runs.
